# План: сайт-генератор персонажей

## 0. Что уже есть (инвентаризация)

| Файл | Строк | Роль |
|---|---|---|
| `char_generator.py` | 1374 | движок: палитры, архетипы, позы, сел-шейдинг, спрайт-лист, CLI |
| `pixelcanvas.py` | 259 | мини-библиотека: Canvas, Mask, PNG-writer (zlib+struct, без зависимостей) |
| `characters.example.json` | 56 | контракт данных: `characters.<id>.materials / .arch` |
| `legacy/char_generator_32x48.py` | 340 | старая версия 32x48 — справка, в сайт не идёт |
| `preview/roster_x1.png` | 1920×768 | ростер из 6 героев — референс внешнего вида |

Базовый набор: `tetrax, matrix, overlord, sentinel, wraith, brute` — у каждого
своя палитра (robe/armor/skin/eye/neon/neon_soft) и архетип
(head/torso/hand/foot/grip + SHOULDER/WAIST/ARM/LEG/ankle).

**Замеры (эта машина, CPython):**
* один спрайт-лист (`--hero tetrax --scale 1`) — **39.9 с** при 18 кадрах
  (idle 4 + punch 3 + kick 3 + super 4 + stun 2 + slip 2);
* ≈ **2.2 с на кадр** (включая черновой проход `render_frame`);
* ростер из шестерых — **~4 мин**;
* `render_frame` рисует сцену **дважды**: черновик на холсте 128×128 (для
  обрезки вылета) + финал 80×128. То есть ~60 % времени — черновик.

**Решения, зафиксированные с пользователем:** Python-бэкенд с переиспользованием
движка · редактор + ростер + экспорт · хранение в localStorage + JSON ·
запуск локально / в локальной сети.

## 1. Архитектура

```
браузер (Vite + React + TS)          локальный сервер (FastAPI + uvicorn)
┌───────────────────────────┐        ┌──────────────────────────────────┐
│ Editor: палитра/архетип   │  POST  │  схема (pydantic)                │
│ Preview: спрайт-лист      │───────▶│  рендер по СПЕЦИфикаЦИИ           │
│ Player: анимации          │◀───────│    engine.CharSpec.from_json()   │
│ Roster: localStorage      │  PNG   │    render_frame / build_sheet    │
│ Export: png + json        │        │  LRU-кэш кадров + пул процессов   │
└───────────────────────────┘        │  очередь долгих экспортов (SSE)  │
                                     │  char_generator.py + pixelcanvas.py│
                                     └──────────────────────────────────┘
```

Ключевое: **пиксели рисует тот же код, что и CLI**. Сайт не «похож на»
генератор — он его вызывает. Отсюда главное техническое требование к рефакторингу:
рендер должен идти от *спецификации*, а не от *id в глобальном словаре*.

## 2. M1. Движок: тонкий API-слой (без изменения картинки)

Сейчас `MATERIALS` / `ARCH` / `HEROES` — глобальные мутабельные словари, а
`build_parts` / `_draw` читают `ARCH[hero]`, `MATERIALS[hero]` по id. Для
веб-сервера это ловушка: два параллельных запроса разных черновиков
перетирают друг другу состояние.

Правка (около 8 мест вызова, логика отрисовки не трогается):

```python
@dataclass(frozen=True)
class CharSpec:
    id: str
    mats: dict          # движковый формат (mat(...))
    arch: dict

    @staticmethod
    def from_json(data: dict) -> "CharSpec": ...   # принимает формат characters.json
    def to_json(self) -> dict: ...                 # обратно в characters.json
    def register_into(self, hero_id: str) -> None: # для CLI

def char_spec(hero_id: str) -> CharSpec: ...      # из MATERIALS/ARCH
```

`_draw(pose, spec, cv, w)`, `render_frame(pose, spec)`, `build_sheet(spec)`,
`head_extent(spec)`, `measure_heads(spec)` — принимают spec. `load_characters()`
остаётся как есть (CLI), но реализуется поверх `CharSpec`.

Что это даёт:
* сервер stateless — черновик не может утечь в другой запрос;
* спецификация = JSON → фронтенд держит ровно тот же контракт, что и CLI
  (никакого обратного конструирования RGBA-кортежей);
* будущий порт в TS/WASM тривиален — данных достаточно, глобалов нет;
* `--list`, `--hero`, `--write` продолжают работать без изменений.

Плюс три мелочи:
* `GET /api/schema` собирается из движка: список вариантов head/torso/hand/foot/grip,
  числовые границы (SHOULDER/WAIST/ARM/LEG/ankle, spec_lam, spec_glow), сетка анимаций.
  Фронтенк генерирует из неё свои TS-типы → расхождение схем ловится тестом.
* предупреждения генератора (рост < 4.0 голов, узкое плечо относительно талии…)
  как список строк — сейчас их нет вообще, а в редакторе они полезны.

**Приёмка:** CLI даёт байт-в-байт те же PNG, что и до рефакторинга (см. M0).

## 3. M0. Сторож: golden-тесты (делается первым, до любых правок)

```
tests/
  golden/            <- эталонные PNG (6 героев x 18 кадров, закоммитить)
  test_parity.py    <- перерисовывает и сравнивает побайтово
  make_golden.py    <- пересоздать эталон (--update)
```

Без этого любая оптимизация (а они будут, см. §5) — русская рулетка с
пиксель-артом. Тест: `py tests/test_parity.py` — 108 кадров (6 героев × 18), ~4 мин,
годится и вручную, и в CI.

## 4. API бэкенда

| Метод | Путь | Ответ | Назначение |
|---|---|---|---|
| GET | `/api/schema` | JSON | сетка анимаций, варианты архетипа, границы чисел, FW/FH/COLS/ROWS |
| GET | `/api/presets` | JSON | 6 базовых героев как спецификации (+ краткие описания) |
| POST | `/api/preview` | PNG | 1 кадр выбранной анимации, `?scale=3` |
| POST | `/api/measure` | JSON | рост в головах + предупреждения (без рендера) |
| POST | `/api/jobs` | `{jobId}` | долгие задачи: `kind: sheet\|roster`, payload |
| GET | `/api/jobs/{id}` | `{status,done,total}` | прогресс |
| GET | `/api/jobs/{id}/events` | SSE | то же, потоком |
| GET | `/api/jobs/{id}/file` | PNG | результат |
| POST | `/api/save` | JSON | записать PNG в `out/<id>.png` + дописать героя в `characters.local.json` |

Заголовки ответа `/api/preview`: `X-Heads` (рост в головах), `X-Render-Ms`,
`X-Cache: hit|miss` — их видно прямо в devtools, это удобный диагностический
инструмент, а не только украшение.

Почему `jobs`, а не просто `POST /api/sheet`: лист — это 40 с (после оптимизаций
≈ 10–15 с), это перебор для синхронного запроса и для любого таймаута
прокси. Очередь + прогресс решают это честно.

**Двусторонняя связь с CLI** (фича M7): `save` пишет ассет в `out/` и правит
`characters.local.json` — дальше `py char_generator.py --characters
characters.local.json --list` покажет новых героев, а `--hero all` соберёт
ростер вместе с ними. Сайт и CLI работают с одной библиотекой, а не как две
отдельные вселенные.

## 5. Производительность (главный риск плана)

Порядок работ, каждый шаг — за прогоном `test_parity.py`:

| # | Что | Ожидаемо | Риск |
|---|---|---|---|
| 1 | LRU-кэш кадров по ключу `hash(spec)+anim+frame+scale` | повторные показы и переключение анимаций — мгновенно | нет |
| 2 | Убрать черновой проход: вместо пиксельного обхода брать bbox суставов + максимальный радиус конечности | ×2.3–2.6 к скорости кадра (черновик — 60 % работы, площадь 128×128 против 80×128) | средний: сдвиг кадра может «поехать» на 1 px — ловится паритетом |
| 3 | Пул процессов (`ProcessPoolExecutor`, по числу ядер) для листов и ростера | лист ≈ 40/N с; прогресс по кадрам | нет |
| 4 | Микро-оптимизация горячих циклов `pixelcanvas` (`has`/`add` инлайн в `distance_field`, `contour`, `dilate`, `cel_fill`) | ещё ×1.5–2 | средний, только за паритетом |
| 5 | Проверить наличие PyPy (`pypy3 -V`) | ×3–5 без единой правки движка | нет, но может не быть в наличии |
| 6 | «Быстрое» превью: пререндер 6 пресетов в стартовый кэш при подъёме сервера | 0 задержка на первом показе | нет |

Целевая цифра: **кадр ≤ 0.5 с**, лист из 18 кадров ≤ 12 с, ростер из 6 героев
(108 кадров) ≤ 60 с.

**UX независимо от скорости:** дебаунс 200 мс, `AbortController` на устаревшие
запросы, поверх превью показывается последний удачный кадр с пометкой «считаем…»,
при перетаскивании слайдера рендер по `pointerup` + раз в 300 мс.

Если после шагов 1–5 кадр всё ещё > 1 с — план Б: превью рисуется в урезанном
режиме (без контура/неона/контактной тени, флаг `--fast`), финальные экспорты
полноценные. Лучше честно пометить превью как «черновик», чем показывать
картинку, которой в экспорте не будет.

## 6. Фронтенд

Стек: Vite + React + TypeScript, состояние — zustand, без тяжёлых UI-китов
(внутренний инструмент, а не лендинг).

**Экран редактора** — две колонки:

*Левая (панель управления):*
* **Палитра** — 9 цветов (`robe` hi/base/dark, `armor`, `skin`, `eye`, `neon`,
  `neon_soft`) + опциональный `spec` для брони/кожи + слайдеры `spec_lam`,
  `spec_glow`. Рядом с каждым цветом — «эталон» из базовых палитр в один клик.
* **Архетип** — 5 селектов (head / torso / hand / foot / grip) с мини-иконками.
* **Пропорции** — 4 числовых слайдера с шагом 1 px (SHOULDER, WAIST, ARM, LEG)
  и `ankle` шагом 0.02. Рядом — предупреждения и рост в головах.
* **Служебное** — «случайный герой» (палитра по правилам гармонии + случайный
  архетип в осмысленных пределах), сброс к пресету, undo/redo.

*Правая (предпросмотр):*
* табы анимаций `idle / punch / kick / super / stun / slip` + плеер с fps;
* переключатель масштаба 1×/2×/3×/4× (`image-rendering: pixelated`, только
  целые множители — иначе пиксель-арт мылится);
* фон: шахматка / однотонный / сетка границ кадра (80×128);
* индикатор «считаем…» поверх последнего удачного кадра.

*Панель ростера:* пресеты + свои персонажи, миниатюра = idle кадр 0 (рендерится
один раз при сохранении и кэшируется в localStorage как data-URL), поиск, теги,
перетаскивание порядка, клик — загрузить в редактор.

*Панель экспорта:*
* `spritelist.png` 320×768 (1:1, как для движка);
* `preview_x3.png` — контактный лист для быстрого взгляда;
* `characters.json` — в формате текущего `characters.example.json`, чтобы
  скормить CLI через `--characters`;
* «сохранить в проект» — запись в `out/` + `characters.local.json`;
* «экспортировать всю библиотеку» — один JSON со всеми своими героями.

**Данные в браузере:** `localStorage["cg.characters.v1"]` — массив спецификаций
с id, именем, тегами, датой, миниатюрой. Плюс автосохранение черновика
редактора отдельно, чтобы перезагрузка страницы ничего не теряла.
Схема версионируется префиксом `v1`, при неизвестной версии — понятная ошибка,
а не тихий сброс.

## 8. Риски

| Риск | Как закрываем |
|---|---|
| Рендер 1.7 с/кадр убьёт «живое» ощущение | M8 (план из §5) + дебаунс/кэш/отмена; если не хватит — режим `--fast` для превью |
| Оптимизации разъедут пиксели | golden-тест M0, каждый шаг §5 — только после зелёного прогона |
| Утечка глобального состояния между запросами | M1: рендер по `CharSpec`, без глобальных id |
| Расхождение TS-типов и Python-схемы | схема генерируется движком, тест сверяет с закоммиченным файлом |

| Правка движка ломает CLI у пользователя | CLI остаётся рабочим путём на каждом шаге; тест запускает и CLI, и API |

## 9. Осознанно не делаем в v1

База данных и авторизация · мультипользовательский режим · серверная
библиотека персонажей (сначала localStorage, точка расширения — один интерфейс
`Storage`) · мобильная вёрстка (инструмент для десктопа) · экспорт в
другие форматы кроме PNG/JSON (Lottie, ASE и т. п.) · автоматический подбор
палитры по нейросети.
