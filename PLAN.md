# План: сайт-генератор персонажей

## 0. Что уже есть (инвентаризация)

| Файл | Строк | Роль |
|---|---|---|
| `char_generator.py` | 1374 | движок: палитры, архетипы, позы, сел-шейдинг, спрайт-лист, CLI |
| `pixelcanvas.py` | 259 | мини-библиотека: Canvas, Mask, PNG-writer (zlib+struct, без зависимостей) |
| `characters.example.json` | 56 | контракт данных: `characters.<id>.materials / .arch` |
| `legacy/char_generator_32x48.py` | 340 | старая версия 32x48 — справка, в сайт не идёт |
| `preview/roster_x1.png` | 1920×768 | ростер из 6 героев — референс внешнего вида |

Базовый набор: `tetrax, matrix, overlord, sentinel, wraith, brute` — у каждого
своя палитра (robe/armor/skin/eye/neon/neon_soft) и архетип
(head/torso/hand/foot/grip + SHOULDER/WAIST/ARM/LEG/ankle).

**Замеры (эта машина, CPython):**
* один спрайт-лист (`--hero tetrax --scale 1`) — **39.9 с** при 18 кадрах
  (idle 4 + punch 3 + kick 3 + super 4 + stun 2 + slip 2);
* ≈ **2.2 с на кадр** (включая черновой проход `render_frame`);
* ростер из шестерых — **~4 мин**;
* `render_frame` рисует сцену **дважды**: черновик на холсте 128×128 (для
  обрезки вылета) + финал 80×128. То есть ~60 % времени — черновик.

**Решения, зафиксированные с пользователем:** Python-бэкенд с переиспользованием
движка · редактор + ростер + экспорт · хранение в localStorage + JSON ·
запуск локально / в локальной сети.

## 1. Архитектура

```
браузер (Vite + React + TS)          локальный сервер (FastAPI + uvicorn)
┌───────────────────────────┐        ┌──────────────────────────────────┐
│ Editor: палитра/архетип   │  POST  │  схема (pydantic)                │
│ Preview: спрайт-лист      │───────▶│  рендер по СПЕЦИфикаЦИИ           │
│ Player: анимации          │◀───────│    engine.CharSpec.from_json()   │
│ Roster: localStorage      │  PNG   │    render_frame / build_sheet    │
│ Export: png + json        │        │  LRU-кэш кадров + пул процессов   │
└───────────────────────────┘        │  очередь долгих экспортов (SSE)  │
                                     │  char_generator.py + pixelcanvas.py│
                                     └──────────────────────────────────┘
```

Ключевое: **пиксели рисует тот же код, что и CLI**. Сайт не «похож на»
генератор — он его вызывает. Отсюда главное техническое требование к рефакторингу:
рендер должен идти от *спецификации*, а не от *id в глобальном словаре*.

## 2. M1. Движок: тонкий API-слой (без изменения картинки) — **сделано**

Сейчас `MATERIALS` / `ARCH` / `HEROES` — глобальные мутабельные словари, а
`build_parts` / `_draw` читают `ARCH[hero]`, `MATERIALS[hero]` по id. Для
веб-сервера это ловушка: два параллельных запроса разных черновиков
перетирают друг другу состояние.

Сделано: введён `CharSpec` (id + палитра + архетип), вся отрисовка принимает
спецификацию, а словари остались реестром и мостом `char_spec(hero_id)`.

```python
spec = CharSpec.from_json(hero_id, data)   # мержит поверх существующего персонажа
spec.to_json()                             # обратно в формат characters.json
spec.register()                            # для CLI
```

`render_frame(pose, spec)`, `build_sheet(spec)`, `head_extent(spec)`,
`measure_heads(spec)`, `build_roster(specs)` — принимают spec.
`load_characters()` остался как был (CLI), но реализован поверх `CharSpec`.

Что это дало:
* сервер stateless — черновик не может утечь в другой запрос;
* спецификация = JSON → фронтенд держит ровно тот же контракт, что и CLI;
* будущий порт в TS/WASM тривиален — данных достаточно, глобалов нет;
* `--list`, `--hero`, `--write` работают как раньше.

Плюс:
* `schema_json()` — варианты архетипа, числовые границы, сетка анимаций;
  отдаётся сайту фронтенку, чтобы TS-типы собирались из данных движка.
  CLI-флаг: `--dump-schema`.
* `validate_spec(data, hero_id)` — ошибки до рендера (неизвестная голова, число
  вне границ, недостающая палитра). У существующего персонажа проверяются только
  перечисленные ключи — остальные наследуются, как и в `from_json`.
* `spec_warnings(spec)` — подсказки редактору: тона не по светлоте, плечи не
  шире талии, рука толще трети плеча, глаз и неон одного цвета. Откалибровано
  так, чтобы шестеро базовых проходили молча; принимает недозаполненный черновик.

**Приёмка выполнена:** golden-тест зелёный — 108 кадров совпали попиксельно после
рефакторинга. Плюс `tests/test_spec_api.py`: 45 проверок (round-trip, слияние,
валидация, схема, границы) — все зелёные.

Найденные и починенные по дороге:
* `mat_to_json` терял `spec_lam`/`spec_glow` у материалов без блика (читал их
  через `mat_spec`, который для `spec=None` отдаёт нули) — материал возвращался
  в CLI с другими значениями по умолчанию;
* `spec_warnings` падал на черновике без палитры, а редактор зовёт её на каждом
  движении слайдера.

## 3. M0. Сторож: golden-тесты (делается первым, до любых правок)

```
tests/
  golden/<hero>.png           <- эталонный спрайт-лист (320x768), закоммитить
  golden/<hero>.measure.json  <- эталонный рост в головах
  test_parity.py              <- перерисовывает и сравнивает ПОПИКСЕЛЬНО
  png_reader.py               <- чтение PNG для теста (в движке нет по нужде)
```

Запуск: `py tests\test_parity.py` — проверка (код 0 = совпало),
`--update` — перезаписать эталон, `--hero X` / `--anim punch` — сузить проверку.
Полный прогон: 6 героев × 18 кадров пулом из 8 процессов ≈ **70 с**.

Без этого любая оптимизация (а они будут, см. §5) — русская рулетка с
пиксель-артом. Сравнение идёт по пикселям, а не по байтам файла: zlib на разных
машинах жмёт одинаковые данные по-разному, и побайтовое сравнение `.png` падало
бы из-за другой версии библиотеки.

Проверено в обе стороны: на сдвиге `LIGHT` тест находит расхождение во всех 18
кадрах tetrax и возвращает код 1; на чистом движке — «ок» по всем шестерым.

## 4. API бэкенда — **сделано (M2)**

**Стек изменён: только стандартная библиотека, без FastAPI.** Проект держится
на требовании «никаких зависимостей», и оно того стоит: репозиторий должен
запускаться командой `py` без `pip install`. Всё, ради чего обычно и берут
веб-фреймворк, уже есть в движке: `validate_spec` проверяет описание,
`schema_json` отдаёт схему. Осталось раздать JSON и PNG — это `ThreadingHTTPServer`.

| Метод | Путь | Ответ | Назначение |
|---|---|---|---|
| GET | `/api/schema` | JSON | сетка анимаций, варианты архетипа, границы чисел |
| GET | `/api/presets` | JSON | 6 базовых героев как спецификации |
| GET | `/api/health` | JSON | живо ли, сколько в кэше |
| POST | `/api/preview` | PNG | 1 кадр, `?anim/frame/scale`; заголовки `X-Render-Ms`, `X-Cache` |
| POST | `/api/measure` | JSON | рост в головах + предупреждения |
| POST | `/api/jobs` | `{jobId}` | долгие задачи: `kind: sheet\|roster` |
| GET | `/api/jobs/<id>` | `{status,done,total}` | прогресс (опросом, не SSE) |
| GET | `/api/jobs/<id>/file` | PNG | результат |
| POST | `/api/save` | JSON | записать PNG в `out/<id>.png` + героя в `characters.local.json` |

**Долгие задачи вместо синхронного ответа:** лист из 18 кадров — это десятки
секунд, такой запрос упирается в любой таймаут. Очередь в памяти + опрос
статуса решают это честно и без SSE.

**Двусторонняя связь с CLI** работает: `POST /api/save` пишет ассет в `out/` и
правит `characters.local.json` — после этого `py char_generator.py --characters
characters.local.json --list` показывает нового героя. Проверено вручную.

### Что дало измерение

Первая версия отдавала лист и ростер одной задачей в одном работнике — пул
процессов при этом не давал ничего (24.4 с на 4 ядрах, как и в одном). Переделано
на «одна задача = один кадр», сборка листа остаётся в главном процессе:

| | лист из 18 кадров |
|---|---|
| один поток | 24.4 с |
| пул из 4 | **8.8 с** |

И главное: собранный по кадрами лист **побайтово равен** `build_sheet()` — это
проверяется в тесте, а не на глаз.

Кадры между процессами передаются плоским массивом RGBA по 4 байта на пиксель
(40 КБ на кадр): pickle холста — список списков кортежей — на порядок тяжелее.

**Приёмка:** `tests/test_server.py` — 30 проверок, включая «лист из сервера
равен эталону CLI» и «пул даёт тот же байт-в-байт результат».

## 5. Производительность (главный риск плана)

Порядок работ, каждый шаг — за прогоном `test_parity.py`:

| # | Что | Ожидаемо | Риск |
|---|---|---|---|
| 1 | LRU-кэш кадров по ключу `hash(spec)+anim+frame+scale` | повторные показы и переключение анимаций — мгновенно | нет |
| 2 | Пул процессов, одна задача = один кадр | **сделано в M2:** лист 24.4 → 8.8 с на 4 процессах, байт-в-байт тот же результат | нет |
| 3 | Убрать черновой проход: вместо пиксельного обхода брать bbox суставов + максимальный радиус конечности | ×2.3–2.6 к скорости кадра (черновик — 60 % работы, площадь 128×128 против 80×128) | средний: сдвиг кадра может «поехать» на 1 px — ловится паритетом |
| 4 | Микро-оптимизация горячих циклов `pixelcanvas` (`has`/`add` инлайн в `distance_field`, `contour`, `dilate`, `cel_fill`) | ещё ×1.5–2 | средний, только за паритетом |
| 5 | Проверить наличие PyPy (`pypy3 -V`) | ×3–5 без единой правки движка | нет, но может не быть в наличии |
| 6 | «Быстрое» превью: пререндер 6 пресетов в стартовый кэш при подъёме сервера | 0 задержка на первом показе | нет |

Целевая цифра: **кадр ≤ 0.5 с**, лист из 18 кадров ≤ 12 с, ростер из 6 героев
(108 кадров) ≤ 60 с.

**UX независимо от скорости:** дебаунс 200 мс, `AbortController` на устаревшие
запросы, поверх превью показывается последний удачный кадр с пометкой «считаем…»,
при перетаскивании слайдера рендер по `pointerup` + раз в 300 мс.

Если после шагов 1–5 кадр всё ещё > 1 с — план Б: превью рисуется в урезанном
режиме (без контура/неона/контактной тени, флаг `--fast`), финальные экспорты
полноценные. Лучше честно пометить превью как «черновик», чем показывать
картинку, которой в экспорте не будет.

## 6. Фронтенд

Стек: **обычные ES-модули, без сборки и без зависимостей.** Планировался Vite +
React + TypeScript, но бэкенд мы сделали на stdlib ради одной команды запуска, и
Node-стек ломал бы то же обещание со стороны фронтенда. Смена решения обратная
не нужна: если интерфейс перерастёт (~1000 строк DOM), `api.js` и `store.js`
остаются как есть, а меняется только слой представления.

* `web/index.html`, `web/app.css`, `web/js/{main,api,store,editor}.js`;
* сервер отдаёт `web/` напрямую (а `web/dist`, если он появится, — победит);
* варианты и границы приходят из `/api/schema`, дублировать их в разметке нельзя.

**Экран редактора** — две колонки:

*Левая (панель управления):*
* **Палитра** — 9 цветов (`robe` hi/base/dark, `armor`, `skin`, `eye`, `neon`,
  `neon_soft`) + опциональный `spec` для брони/кожи + слайдеры `spec_lam`,
  `spec_glow`. Рядом с каждым цветом — «эталон» из базовых палитр в один клик.
* **Архетип** — 5 селектов (head / torso / hand / foot / grip) с мини-иконками.
* **Пропорции** — 4 числовых слайдера с шагом 1 px (SHOULDER, WAIST, ARM, LEG)
  и `ankle` шагом 0.02. Рядом — предупреждения и рост в головах.
* **Служебное** — «случайный герой» (палитра по правилам гармонии + случайный
  архетип в осмысленных пределах), сброс к пресету, undo/redo.

*Правая (предпросмотр):*
* табы анимаций `idle / punch / kick / super / stun / slip` + плеер с fps;
* переключатель масштаба 1×/2×/3×/4× (`image-rendering: pixelated`, только
  целые множители — иначе пиксель-арт мылится);
* фон: шахматка / однотонный / сетка границ кадра (80×128);
* индикатор «считаем…» поверх последнего удачного кадра.

*Панель ростера:* пресеты + свои персонажи, миниатюра = idle кадр 0 (рендерится
один раз при сохранении и кэшируется в localStorage как data-URL), поиск, теги,
перетаскивание порядка, клик — загрузить в редактор.

*Панель экспорта:*
* `spritelist.png` 320×768 (1:1, как для движка);
* `preview_x3.png` — контактный лист для быстрого взгляда;
* `characters.json` — в формате текущего `characters.example.json`, чтобы
  скормить CLI через `--characters`;
* «сохранить в проект» — запись в `out/` + `characters.local.json`;
* «экспортировать всю библиотеку» — один JSON со всеми своими героями.

**Данные в браузере:** `localStorage["cg.characters.v1"]` — массив спецификаций
с id, именем, тегами, датой, миниатюрой. Плюс автосохранение черновика
редактора отдельно, чтобы перезагрузка страницы ничего не теряла.
Схема версионируется префиксом `v1`, при неизвестной версии — понятная ошибка,
а не тихий сброс.

устаревшие запросы отменяются, масштаб подбирается под окно.

Критический путь: **M0 → M1 → M2 → M3**. Дальше этапы независимы и
делаются в любом порядке.

## 9. Осознанно не делаем в v1

База данных и авторизация · мультипользовательский режим · серверная
библиотека персонажей (сначала localStorage, точка расширения — один интерфейс
`Storage`) · мобильная вёрстка (инструмент для десктопа) · экспорт в
другие форматы кроме PNG/JSON (Lottie, ASE и т. п.) · автоматический подбор
палитры по нейросети.

## 11. Куда это движется (замысел)

Проект нужен шире, чем «ещё боец»: генератор персонажей **разных стилей**,
**разной одежды** и **разных жанров** — от чиби до реализма, от киберпанка до
фэнтези, для файтинга, битемапа и приключенческих игр. На первом этапе вид сбоку,
на зрелом — спрайты в объёме.

### Ориентиры

Четыре игры, по которым выбираются решения. Это **язык, а не образец для
копирования**: пропорции, вес удара, читаемость одежды.

| игра | что от неё берём | чем это уже сделано | чем ещё нет |
|---|---|---|---|
| **The Friends of Ringo Ishikawa** | рост в головах и карикатурность: выше и тоньше, голова мелкая | `style.head` умеет и крупную, и мелкую голову; метрика роста честная | кадр шире и выше 80×128; тело тоньше (сейчас ~5 голов, у Ишикавы около 6.5) |
| **Streets of Rage 3** | персонаж узнаётся по одежде и походке, а не по цвету | 8 слотов одежды + форма одежды, 10 комплектов | походка пока 4 кадра; узнаваемость читается плохо |
| **Mortal Kombat II** | у каждого удара своя длительность, своё активное окно, своя зона | `ms` по кадрам, хитбоксы, хёртбоксы, `combat.json` в архиве | нет отскока, блока с уроном, воздушной фазы ударов |
| **Golden Axe III** | вес: широкие плечи, крупные кисти, отход длиннее замаха | `SHOULDER`, `ARM`, `LEG` в архетипе; тайминги ударов различаются | нет «размаха» — удара с задержкой перед контактом и с доводкой после |

Практические следствия, которые видно в коде:

* **Кадр должен стать параметром стиля.** Сейчас `FW, FH` — константы, а позы
  заданы абсолютными пикселями. Ишикава требует другого кадра, значит это не
  отложить «на потом».
* **Рост в головах — параметр, а не следствие.** Сейше 5.04 у базового
  бойца; целевые 5 (Golden Axe) и 6.5 (Ишикава) должны быть достижимы
  выбором, а не правкой константы.
* **Вес удара — это тайминги плюс поза.** Сейчас замах короче отхода, но нет
  кадра доводки, когда удар уже не бьёт, а противника ещё отбрасывает.

### Что уже этому не мешает

* **Скелет = точки суставов.** Анимации уже описываются координатами суставов,
  а не картинками: новый удар — это числа, а не перерисовка.
* **Материалы отделены от формы.** Палитра и архетип разнесены, меняется одно —
  не трогается другое.
* **Персонаж описан данными.** Описание не знает, рисует его пиксельный движок
  или что-то ещё.

### Что мешает — и это надо знать до того, как дойдёт до дела

| Узкое место | Где в коде | Почему мешает |
|---|---|---|
| Пропорции тела зашиты в координаты поз | `base_pose()` и соседние функции: абсолютные пиксели | **Осталось главным**: чиби с крупной головой — это всё ещё чиби на теле бойца. Нужно другое тело, а не только другая голова |
| Голова сжимается одним коэффициентом | `HEAD_K = 0.71`, `HEAD_CHIN_Y`, `HEAD_TOP` | **Закрыто**: стало `style.head`, множитель в спецификации |
| Одежда — это два материала | `robe` / `armor`, а что надето, выводится из `grip` | Современная одежда, доспех, плащ, штаны, волосы в такую модель не помещаются: нужен слот, а не «ряса или броня» |
| Свет — три жёсткие полосы | `_shade_band` | **Закрыто**: `style.bands` 2…6 полос на той же трёхтональной рампе |
| Анимации — функции в коде | `ANIMS` | Ходьба, приседание, прыжок, блок, падение, уклонение — это десятки новых функций вместо записей в файл |
| Сетка листа фиксирована | `COLS, ROWS = 4, 6` | С двадцатью анимациями шестьстрочная сетка перестаёт работать |
| Кадр фиксирован | `FW, FH = 80, 128` | Битэмапу нужен другой кадр, чем файтингу |

Вывод: **скелет и материалы — в порядке, фигура — в коде.** Пока позы и
пропорции живут в Python, каждый новый стиль стоит как новый модуль движка.

### Путь

| Шаг | Что | Открывает |
|---|---|---|
| **1. Стиль как профиль** | `style.json`: доля головы, пропорции тела, число световых полос, толщина контура, кадр, набор анимаций | **сделан на 3/5**: доля головы, полосы света, контур — см. «Стиль-профиль» ниже; остались пропорции тела и кадр |
| **2. Позы данными** | анимации в JSON рядом с описанием персонажа, с таймингами и (для файтинга) хитбоксами | **сделан**: 23 движения, `ms` по кадрам, хитбоксы и хёртбоксы |
| **3. Слоты одежды** | голова/волосы, торс, руки, ноги, стопы, пояс, плащ; пустой слот — голая кожа | **сделан**: восемь слотов, 10 комплектов |
| **3a. Форма одежды** | слот получает не только материал, но и форму: длина рукава и штанов, плащ, воротник, пояс, наплечники | **сделано**: шесть параметров формы, все 10 комплектов их используют |
| **4. Экспорт рига** | тот же скелет в JSON для внешнего 3D-инструмента | пиксельный рендер становится одним из потребителей описания, а не единственным |

Шаги идут в этом порядке сознательно: стиль задаёт пропорции, позы читают
пропорции, одежда ложится на позы, экспорт рига нужен последним.

**Шаги 1 (3/5), 2 и 3 сделаны.** Осталось: пропорции тела и кадр в стиле,
экспорт рига.

### Что дальше по шагу 1 — и почему именно это

Ориентиры из §11 превращают «пропорции тела» в конкретную задачу: базовый
боец сейчас 5.04 головы при плечах 26 и кисти 6. Для Streets of Rage и
Golden Axe это верно, для Ringo Ishikawa нужен рост 6.5 голов и тонкая
фигура, для чиби — наоборот 3.5.

| Параметр | Куда | Почему так |
|---|---|---|
| `frame` (`w`, `h`) | стиль | Ишикава не влезет в 80×128: персонаж выше, а кадр общий на всех. Позы придётся хранить в относительных единицах, иначе смена кадра ломает анимацию |
| `build` (плечи, талия, руки, ноги, шея) | стиль, поверх архетипа | архетип — это «какая форма» (шлем, плащ), а пропорции — «какого размера». Смешивать их нельзя: у рыцаря с широкими плечами и у худого бойца один и тот же архетип |
| `stance` | позы | вес и размах читаются стойкой: Golden Axe — широкая, Ишикава — узкая |

**Порядок важен:** сначала относительные позы, потом смена кадра. Иначе придётся
дважды переписывать: позы в пикселях не масштабируются, а масштабировать их
придётся именно для Ишикавы.

### Что можно сделать дёшево и сразу

* **Доля головы в описании персонажа.** Сейчас `HEAD_K` — константа модуля;
  перенести её в спецификацию — десяток строк, и «большеголовая» версия того же
  бойца получается сразу. Это 80 % эффекта чиби при 5 % работы и первая проверка,
  что путь «стиль = данные» вообще работает. **Сделано** — это `style.head`.
* **Анимации в JSON.** Позы — это уже просто словари чисел; вынести их в файл
  и грузить оттуда — mechanical работа, после которой анимацию можно добавить
  правкой файла. **Сделано.**

### Чего пока не делаем

3D — это отдельный проект, а не режим генератора. Здесь важно лишь одно:
описание персонажа не должно знать про пиксели. Сейчас оно знает ровно настолько,
насколько это неизбежно для материала (три тона сел-шейдинга) — и это переживёт
перенос в 3D без потерь.

## 11a. Библиотека движений (сделано)

Анимации переехали из кода в `data/animations.json`. Кадр — список операций
над скелетом:

```json
{"shift": {"parts": ["head", "neck", "chest"], "dx": 0, "dy": 20}}
{"aim":   {"side": "f", "d": [27, 2], "bend": 1.0}}
{"step":  {"side": "b", "d": [-5, -1], "bend": 1.0}}
```

* `shift` двигает все суставы или перечисленные (`parts` — список: при присед��нии
  корпус идёт вниз, а стопы остаются на полу);
* `aim`/`step` тянут кисть или стопу на смещение от опорной стойки, промежуточный
  сустав считается двухзвенной IK.

Почему смещения, а не координаты: иначе анимация была бы привязана к одному телу
и к 80×128. Со смещениями один и тот же `walk` работает и на низком бойце, и на
хэви-меке — как только появится выбор тела.

**23 движения** в пяти разделах: покой, движение (walk, run, crouch, jump, fall,
land, dash), защита, атака (jab, cross, hook, uppercut, low_kick, round_kick,
knee, throw, punch, kick, super), реакция.

Интерфейс: вкладки показывают всю библиотеку (посмотреть можно любое движение),
галочки «Движения в наборе» задают состав выгрузки. Лист строится под выбранный
набор: строк столько, сколько движений, колонок — сколько кадров в самом
длинном.

Выгрузка отдаёт zip: общий лист, отдельный PNG на каждое движение, описание
персонажа и `README.txt` с раскладкой.

Проверено: перевод шести прежних анимаций в данные дал **те же 108 пикселей**
(golden-тест зелёный) — формат не врёт.

Что дальше по этой дороге: тайминги и хитбоксы в описании анимации (для
файтинга), а затем — пропорции тела и экспорт рига.

### Найденная по дороге латентная ошибка

`_draw_outline` строит список «что лежит сверху каждого слоя» в обратном
порядке, а читает как прямой — индексы сдвинуты. Ошибка была невидима, пока в
список слоёв никто не добавлял: сдвиг на одну позицию просто оставлял часть
чужих контуров поверх соседей. Добавление плаща в общий список её вскрыло —
36 пикселей на кадр.

Сама ошибка **не исправлена намеренно**: исправление меняет обводки всех
шестерых базовых бойцов, то есть это изменение картинки, а не кода. Оно
записано здесь, чтобы сделать отдельным осознанным шагом: переписать эталоны,
показать разницу глазами и решить, чей вариант лучше. Плащ нарисован отдельно
по той же причине — так он не сдвигает индексы остальным слоям.

## 11b. Стиль-профиль (сделано частично)

Три параметра стиля вынесены из кода в спецификацию — по одному и тому же
принципу, что слоты одежды: значение не задано → старая картинка.

| параметр | было | стало |
|---|---|---|
| `head` | константа `HEAD_K = 0.71` | множитель 0.6…1.8 от базовой доли головы |
| `bands` | `_shade_band` жёстко даёт 0/1/2 | 2…6 полос на той же трёхтональной рампе |
| `outline` | `contour(m, 1)` | 0…2 пикселя |

**Как устроены N полос.** Границы света не сдвинулись (0.42 и -0.18) — вместо
этого промежуток между ними делится на `bands - 1` шагов, а цвет берётся
интерполяцией **по трём тонам материала**. Отсюда три следствия, и все
удачные:

* `bands = 3` — ровно прежняя картинка, потому что шаги совпадают с
  существующими границами (golden-тест это проверяет);
* `bands = 5` не требует ни новых цветов, ни размытия — «мягкий свет»
  получается интерполяцией внутри материала;
* `bands = 2` схлопывает диапазон в «свет против тени» — грубый плоский стиль,
  одна переменная вместо отдельного режима отрисовки.

**Рост в головах считается с тем же коэффициентом, каким нарисована голова.**
Иначе чиби получил бы «5.04 головы» по старой формуле — метрика врала бы
пользователю ровно в том случае, ради которого он её и смотрит.

**Пропорции тела и размер кадра не тронуты намеренно.** Позы заданы
абсолютными пикселями кадра, поэтому «другое тело» — это другая стойка
скелета (`RIG_STANCE`) с масштабом, а не один множитель. Сделать это
правильно — следующий шаг после таймингов.

`data/styles.json` — 6 образцов (16-бит, чиби, мультяшный, мягкий, жёсткий,
плоский). Стиль накладывается на любого персонажа и любую одежду: рыцарь в
мультяшном стиле — это одна строка, а не новая копия движка.

Проверено в браузере: образец «чиби» → голова 34 px, метрика «3.76 головы»
(было 24 px и 5.04).
